Background

What existed before — the original agent

The previous agent, "Executive Escalations Coordinator" (ID: executive-escalations-dispatcher), was designed to remove the single-person bottleneck in Executive Escalations intake while keeping the Champion responsible for judgment and communication.

The flow was: an escalation email arrived at escalations@hubspot.com → a Gmail filter forwarded it to the Asana Triage project → a new task was created → a Sidekick scheduled task ran every 5 minutes and invoked the full agent → the agent researched the account, selected a Champion, and enriched the task → the Champion picked up the case from Asana.

The Champion remained fully responsible for executive and customer communication, escalation strategy, and resolution. The agent's job was to front-load the research and routing work — not to replace judgment.

What failed in production

Six failures that led to deactivation

The system passed controlled testing but encountered significant failures during the OOO period. The first two below are hard launch blockers; the others are structural weaknesses that made the system brittle to operate.

01
Duplicate detection relied on model judgment

The agent made its own determination about whether a case was new or already active. Under real load this degraded — the agent assigned Champions to cases that were already being worked, creating duplicate ownership.

02
Full agent polled every 5 minutes

The full reasoning agent ran on a fixed 5-minute schedule regardless of whether there was anything to process. This created an unsustainable projected monthly cost.

03
Fragile idempotency via text separator

The only signal that a task had already been processed was the presence of a specific text separator in the Asana notes. This was helpful for readability but too easy to lose through normal note editing.

04
Brittle Glean document retrieval

The prompt required exact title string matches for the Executive Escalations playbooks. When Glean returned the correct document with slightly different metadata, the agent treated it as missing and halted the entire intake.

05
No single kill switch

Stopping the workflow required locating and disabling pieces across three separate systems — Sidekick, Gmail, and Asana — with no documented rollback procedure or named owners.

06
Email reply loop added executives as collaborators

If Champions replied with escalations@hubspot.com still in To/CC, Asana added the email participants — including external executives — as internal task collaborators.

What I investigated

What I validated, and what I couldn't resolve alone

I used Sidekick to validate the proposed rebuild architecture. Throughout the investigation I instructed Sidekick not to build or activate anything — the goal was to confirm whether the design was feasible.

What I was able to validate
  • Created the Dispatcher Status Asana field and confirmed Sidekick can both read and update it. This replaces the text-separator as the authoritative processed-state store.
  • Confirmed that no native Asana event trigger exists in Sidekick. A lightweight polling gate remains the right V1 approach.
  • Confirmed that limiting to 1 task per cycle and writing New → Processing immediately (as the first action) reduces the theoretical race condition to residual risk.
  • Confirmed Asana assignment alone is sufficient as the Champion handoff — the Slack postMessage approval constraint makes Slack unreliable for V1, and Asana is already the authoritative signal.
  • Shared the actual process and playbook documentation with Sidekick so the proposed agent can ground its routing in real process rather than inference.
What I could not resolve alone
  • Sidekick found additional Asana projects beyond Executive Escalations Triage: Executive Escalations - Strategic Accounts (GID: 1211057248458958) and an older project (GID: 1201984215267707). The duplicate check must span every active-escalation source.
  • The process documentation says routing is based on Function + Region, but the original agent also included Segment. I don't want to build routing logic on an assumption here.
  • Sidekick could not find an authoritative Champion roster — only historical assignment names. If one doesn't exist, we need to decide whether to create one and where to maintain it.
Proposed redesign — not approved, not deployed

The four key changes from the original design

The core proposal is to address each of the six failures before rebuilding. This is what the redesign looks like.

  • 01
    Lightweight discovery gate replaces full-agent polling

    Poll every 15 minutes. The gate checks Asana for tasks where Dispatcher Status = New. If none exist, stop — do not invoke the expensive reasoning model. The full Coordinator only runs when there is confirmed work to do.

    Fixes: 5-minute cost problem
  • 02
    Dispatcher Status field as the primary state store

    New → Processing → Processed / Needs Human Review / Failed. The field (GID: 1218925551036138) already exists in Asana. When the agent picks up a task, its first action is to write New → Processing so no other execution can claim the same task. The text separator is kept for readability but is no longer the authoritative check.

    Fixes: fragile text-separator idempotency
  • 03
    Hub ID-based duplicate check before Champion assignment

    Before assigning any Champion, the agent resolves the company's CRM Hub ID and searches all authoritative escalation projects for an exact Hub ID match. If an active case exists for the same issue, the agent does not assign a second Champion — it stops and routes to human review. Model judgment is used to help determine same-vs-different issue, but is never the only protection against duplicate ownership.

    Fixes: duplicate detection failure
  • 04
    Asana assignment as the sole authoritative Champion signal

    Asana assignment is the Champion handoff. Slack is informational and optional. This removes the service-level Slack approval constraint that blocked automated posting in the original build. Communication remains entirely human-owned — the agent drafts, the Champion validates and sends.

    Fixes: Slack approval constraint
✅
Glean retrieval and kill switch also addressed

The proposed agent uses semantic matching for playbook retrieval — retrieval failure is logged and does not halt intake. A documented 5-step kill switch procedure (Sidekick → Gmail filter → Asana rule) is planned as a prerequisite before any go-live.

Open questions

Which Asana projects are the authoritative source for active escalations?
Executive Escalations Triage · Strategic Accounts · Older tickets project		 The duplicate Hub ID check must search every project that holds active cases. If I miss one, the agent could still assign a second Champion to an active case. Before routing logic is built
Is routing based on Function + Region, or Function + Region + Segment? Process documentation says Function + Region. The original agent also used Segment. I don't want to build routing on the wrong criteria. Before routing logic is built
Does an authoritative Champion roster exist somewhere? Without a controlled roster, the agent has no reliable way to determine the current active Champion pool or apply round-robin logic. If one doesn't exist, I'm proposing a simple Google Sheet registry. Before routing logic is built
Who has access to create the Asana Rule that sets new intake tasks to Dispatcher Status = New? I don't have Asana Rules access in this project. Without this rule, intake tasks won't be visible to the discovery gate and the automation won't start correctly. Before any production launch
Is ungated updateTask acceptable given that it enables unattended state changes and automatic Champion assignment? This is a cost and risk tradeoff. Ungating updateTask allows the automation to run fully unattended — which is what we want — but it also removes the approval step that currently slows things down. Before build begins
Is the proposed 15-minute polling architecture and its cost model acceptable? This is significantly lower cost than the original 5-minute full-agent poll, but still involves recurring automation spend. I want to confirm the business cost is acceptable before finalizing the architecture. Before build begins
